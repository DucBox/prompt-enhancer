Prompt Enhancer — Kế hoạch triển khai

Mô-đun trung gian: user prompt → JSON chi tiết làm đầu vào cho model sinh ảnh. Giai đoạn 1 chỉ làm SFT; DPO/GRPO để sau.

Bối cảnh & nguyên tắc cốt lõi

Model sinh ảnh chỉ chạy tốt khi nhận JSON chi tiết và đầy đủ. Nên mô-đun này không chỉ "đổi định dạng" mà phải chi tiết hoá: dù đầu vào ngắn hay dài, đầu ra luôn phải là một JSON dày.

Ta có sẵn 28.000 file JSON (vốn là caption của ảnh thật) nhưng chưa có user prompt. Toàn bộ kế hoạch dưới đây là để sinh ra phần thiếu đó, theo hướng đi ngược: JSON → prompt, rồi train theo chiều xuôi prompt → JSON.

Ba khái niệm dùng xuyên suốt tài liệu
target_json JSON gốc, đầy đủ. Luôn là nhãn Y khi huấn luyện, cho cả 3 mức prompt.
sub_json Phần thông tin mà user "được biết" — một tập con các mệnh đề rút từ target_json. Dùng để sinh prompt và làm checklist chấm điểm. Không bao giờ là nhãn Y.
persona Hồ sơ người viết (vai, ngôn ngữ, độ cẩu thả). Chỉ đổi văn phong, không đổi nội dung.

Ví dụ chạy xuyên suốt

Giả sử một file trong 28k có nội dung rút gọn như sau:

target_json = {
  "high_level_description": "Ảnh chụp ba người bạn trẻ đứng trước Lăng Chủ tịch Hồ Chí Minh ...",
  "style_description": { "aesthetics": "...", "lighting": "nắng sớm", "photo": "...", "medium": "photograph" },
  "compositional_deconstruction": {
    "background": "Quảng trường Ba Đình rộng, bầu trời trong ...",
    "elements": [
      { "id": 0, "type": "obj", "desc": "Nam thanh niên mặc áo sơ mi trắng ..." },
      { "id": 1, "type": "obj", "desc": "Nam thanh niên mặc áo phông đen ..." },
      { "id": 2, "type": "obj", "desc": "Cô gái mặc áo dài trắng ..." },
      { "id": 3, "type": "obj", "desc": "Lăng Chủ tịch Hồ Chí Minh, khối đá granite xám ..." },
      { "id": 4, "type": "obj", "desc": "Hàng cây xanh hai bên quảng trường ..." },
      { "id": 5, "type": "obj", "desc": "Lá cờ đỏ sao vàng trên cột cờ phía xa ..." }
    ]

}
Toàn bộ pipeline 28k target_json │ ├─▶ [0] Chuẩn hoá + audit ──────────▶ target_json sạch, có element id │ ├─▶ [1a] LLM nhóm + phân rã ────────▶ nhóm khái niệm + mệnh đề (cache, đóng băng) │ ├─▶ [1b] CODE nén 2 trục ───────────▶ sub_json theo 3 mức chi tiết │ ├─▶ [2a] LLM verbalize ─────────────▶ user_prompt │ ├─▶ [2b] Lọc / QC ──────────────────▶ loại prompt sai lệch (~15-20%) │ ├─▶ [2c] Chia tập theo id ──────────▶ train / val / test │ ├─▶ [3] Bộ đánh giá + baseline ────▶ thước đo (làm TRƯỚC khi train) │ ├─▶ [4] Huấn luyện SFT ────────────▶ LoRA adapter │ └─▶ [5] Đánh giá ──────────────────▶ báo cáo

Chi tiết từng bước

0 Chuẩn hoá & kiểm định dữ liệu gốc code thuần
Đầu vào
  • 28.000 file .txt (lõi là JSON)
Đầu ra
  • target_json đã sạch, mỗi element có id
  • Báo cáo audit

Làm gì: bỏ bbox và color_palette; kiểm tra schema (photo hoặc art_style, không được cả hai); gán id ổn định cho từng element; thống kê phân phối số element, độ dài, tỉ lệ lỗi, trùng lặp.

Vì sao quan trọng: phân phối số element thu được ở đây chính là ngưỡng tham chiếu cho chỉ số Richness ở bước 5. Và nếu dữ liệu gốc bẩn thì mọi bước sau vô nghĩa.

Dữ liệu gốc rất sạch. Con số đáng chú ý là mỗi desc dài trung bình 19 từ — nó quyết định thiết kế của bước 1b.

1a LLM gom nhóm & phân rã mệnh đề LLM · chạy 1 lần · cache
Đầu vào
  • 1 target_json
Đầu ra
  • Nhóm khái niệm + số lượng (bề rộng)
  • Mệnh đề nguyên tử của từng desc (chiều sâu)

Nhiệm vụ 1 — gom nhóm. Một prompt ngắn có thể nhắc tới một khái niệm nhưng khái niệm đó lại tương ứng với nhiều element. "Nhóm bạn 2 nam 1 nữ" = 1 khái niệm nhưng 3 element. Nếu chỉ đếm element sẽ cắt nhầm.

{
  "concept_groups": [
    { "name": "Lăng Bác",   "member_ids": [3],     "cardinality": "exact:1", "cultural": true },
    { "name": "nhóm bạn",   "member_ids": [0,1,2], "cardinality": "exact:3",
      "cardinality_detail": "2 nam, 1 nữ" },
    { "name": "cảnh nền",   "member_ids": [4,5],   "cardinality": "vague" }
  ]
}

cardinality có hai trạng thái — exact:n khi đếm được chính xác, vague khi mô tả kiểu "nhiều", "một đám". Nhầm chỗ này sẽ sinh ra ràng buộc số lượng sai.

Nhiệm vụ 2 — phân rã mệnh đề. Mỗi desc dài trung bình 19 từ và gói nhiều thông tin vào một câu. Phải tách thành các mệnh đề nhỏ nhất, có xếp hạng, thì mới cắt bớt chiều sâu được ở bước sau.

Ví dụ — phân rã một desc có thật
desc gốc (24 từ):
  "A long purple wooden boat positioned horizontally across the center of the frame,
   serving as a floating restaurant with cooking equipment and passengers aboard."

→ f0  chủ thể : chiếc thuyền        (hạng 0 — luôn giữ)
  f1  thuộc tính: màu tím            (hạng 1)
  f2  thuộc tính: bằng gỗ            (hạng 2)
  f3  thuộc tính: là quán ăn nổi     (hạng 3)
  f4  thuộc tính: dài                (hạng 4)
  f5  vị trí   : nằm ngang giữa khung (hạng 5)
  f6  thuộc tính: có khách trên thuyền (hạng 6)

Tập mệnh đề còn sống sót sau khi cắt chính là checklist chấm điểm ở bước 5 — nên đơn vị chấm điểm là mệnh đề, không phải cả desc.

1b Lắp sub_json — nén theo 2 trục code thuần · có seed
Đầu vào
  • target_json + kết quả bước 1a
Đầu ra
  • 3 sub_json (short / medium / long)
Phải nén cả hai trục, không chỉ một
Chỉ cắt bớt số lượng element là chưa đủ. Vì mỗi desc dài trung bình 19 từ, một prompt "short" giữ 2 element vẫn ra ~38 từ — đặc như JSON, không giống người viết.

Trục bề rộng — giữ bao nhiêu nhóm khái niệm.
Trục chiều sâu — mỗi element giữ bao nhiêu mệnh đề.
MứcBề rộngChiều sâu Độ dài
short Nhóm chính + tối đa 2 nhóm văn hoá Việt + mọi chữ trong ảnh Chỉ chủ thể + 1 thuộc tính (f0–f1); mỗi nhóm tối đa 2 thành viên (nhóm chính: 3) 8–20 từ
medium 40–60% số nhóm, tối đa 3 nhóm văn hoá, thêm gợi ý bối cảnh 1–2 thuộc tính mỗi element; mỗi nhóm tối đa 4 thành viên (nhóm chính: 5) 30–60 từ
long 55–95% số nhóm (ngẫu nhiên), không giới hạn nhóm văn hoá 2–3 thuộc tính; riêng chủ thể chính giữ gần đủ; không giới hạn số thành viên/nhóm 100–200 từ

Đuôi 95% của mức long chính là tình huống user viết cực chi tiết — khi đó việc của model gần như chỉ là bóc tách và dựng lại JSON. Đây là một điểm trên phổ, không phải một chế độ riêng.

Khoảng từ mục tiêu có chuẩn tham chiếu nào không?
Đã research: không có benchmark học thuật/công nghiệp nào định nghĩa "short/medium/long" theo số từ cố định — các mốc phổ biến trên blog prompt engineering chỉ là quy ước, không phải kết quả đo đạc. Đáng chú ý: paper "Harnessing Caption Detailness for Data-Efficient Text-to-Image Generation" (arXiv 2505.15172, 5/2025) phê phán chính cách chọn dữ liệu theo độ dài, đề xuất đo "detailness" bằng Image Coverage Rate × Average Object Detailness — về bản chất là breadth × depth, đúng hai trục pipeline này đã tự chọn từ đầu. Kết luận: hướng hai-trục hiện tại đã khớp tinh thần nghiên cứu mới nhất; khoảng từ mục tiêu (8-20/30-60/100-200) vẫn là tham số tự hiệu chỉnh bằng dữ liệu thật, không có "con số chuẩn" để tra cứu thay thế.
Sự cố thực tế: short/medium dài hơn hẳn mục tiêu
Chạy thử trên dữ liệu server cho thấy prompt short ra tới ~22 từ (mục tiêu 8–20), medium có lúc chạm 88 từ (mục tiêu 30–60). Nguyên nhân không phải ở bước 2a mà ở checklist quá to do bước 1b lắp ra. Ba lỗi cụ thể:

1. Nhóm "bao trọn" bị giữ hết chỉ vì lẫn một mẩu chữ. Một nhóm cảnh nền gộp 13 element không liên quan, tình cờ chứa 1 element chữ (biển hiệu) — luật "giữ mọi chữ trong ảnh" khi đó kéo theo toàn bộ 13 element. Sửa: chỉ giữ đúng phần tử chữ trong nhóm đó, không giữ cả nhóm.

2. Không có trần cho số thành viên một nhóm. Nhóm chính "ba người trên thuyền thúng" một mình đóng góp 12 mệnh đề ở mức short. Sửa: thêm trần cứng theo mức (bảng bên trên).

3. Luật "giữ mọi nhóm văn hoá" không có trần. Một ảnh có 4 nhóm được gắn cờ văn hoá thì cả 4 đều lọt vào short, dù bề rộng mục tiêu của short chỉ là ~1 nhóm. Sửa: thêm trần theo mức, ưu tiên giữ nhóm có độ nổi bật cao hơn (xuất hiện sớm hơn) khi phải loại bớt.

Kết quả đo lại trên 50 ảnh: short — số mệnh đề p90 15→11, max 16→15; medium — p90 29→25, max 44→33. Đây là cải thiện ở checklist (đầu vào bước 2a); độ dài prompt thực tế cần đo lại sau khi chạy lại bước 2a.
Sự cố thực tế: checklist scene mâu thuẫn với chính luật cấm ở bước 2a
Chạy full pipeline (test_5, 100 ảnh) cho thấy tỉ lệ đạt ở bước 2b chỉ 63% (medium) và 62% (long) — thấp hơn hẳn short (77%). Soi 98 prompt bị loại: 80% bị loại vì lý do liên quan tới scene (loại ảnh / góc chụp), gồm hai nguyên nhân:

1. loai_anh = "photograph" chiếm 994/1000 mẫu (99,4%) — gần như hằng số, không phân biệt được gì, nhưng checklist vẫn bắt buộc phải nhắc tới → 44/98 lượt loại chỉ vì "thiếu photograph", dù không có người dùng thật nào tự nhiên nói "đây là một bức ảnh".

2. goc_chup lấy nguyên văn cụm kỹ thuật tiếng Anh (vd "eye-level medium shot, sharp focus") — trong khi chính hệ thống prompt ở bước 2a lại cấm dùng ngôn ngữ kỹ thuật khung hình. Model làm đúng (bỏ qua), nhưng bị 2b chấm sai vì checklist đòi đúng cụm kỹ thuật đó — hai bước tự mâu thuẫn nhau.

Sửa: chỉ đưa loai_anh vào checklist khi khác giá trị mặc định ("photograph"); chỉ đưa goc_chup vào khi câu tả chứa từ khoá góc máy đáng chú ý (high-angle, low-angle, aerial, close-up, wide shot...) — bỏ hẳn khi chỉ là góc mặc định (eye-level, medium shot, deep/sharp focus).
Hai sự cố tiếp theo phát hiện ở test_6 (sau khi sửa scene ở trên)
Chạy lại full pipeline: pass rate nhích lên 83%/70%/66% (short/medium/long) — đỡ hơn hẳn nhưng vẫn còn hai lỗi hẹp:

1. Dữ liệu gốc ghi góc máy không nhất quán. Có ảnh viết "eye-level, wide shot" (tách bằng dấu phẩy), có ảnh viết dính liền "eye-level wide shot" (không dấu phẩy). Ở trường hợp dính liền, việc giữ nguyên cả cụm khiến "eye-level" (mặc định, bị cấm) vẫn lọt theo cùng từ khoá đáng chú ý. Sửa: cắt bỏ các từ mặc định (eye-level) ra khỏi cụm trước khi đưa vào checklist, chỉ giữ lại đúng phần đáng chú ý ("wide shot").

2. Ràng buộc số lượng sai khi tên nhóm đã là danh từ tập hợp/cặp. Với nhóm tên "đôi đũa" (đã tự mang nghĩa "một cặp") có 2 member, code từng ghép thẳng "số lượng: 2 đôi đũa" — đọc thành "2 cặp đũa" (4 chiếc), trong khi ảnh chỉ có đúng 1 đôi (2 chiếc). Bug lộ rõ nhất ở ảnh Cầu Vàng: "đôi bàn tay đá khổng lồ" chỉ có 1 đôi (2 bàn tay) nhưng checklist ghi "2 đôi bàn tay" — sai và không ai đặt hàng ảnh lại nói câu này. Sửa: bỏ hẳn ràng buộc số lượng khi tên nhóm bắt đầu bằng một danh từ tập hợp (đôi/cặp/bộ/cụm...).

27/81 prompt bị loại chỉ vì scene (không dính lỗi nội dung khác) — riêng nhóm này sửa xong đã cứu được khoảng 1/3. Đào tiếp hai nguồn lớn nhất lộ ra 2 vấn đề nữa:

1. Cắt cứng theo số từ để lại cụm cụt (bug thật). first_clause() áp dụng cho bối cảnh nền (medium) từng cắt giữa câu, ví dụ "...framed by a heavy brown wooden door frame on the" — mất chữ "left", cụt lửng. Không ai viết prompt lại chèn một câu bị cắt cụt như vậy. Sửa: sau khi cắt theo số từ, lùi lại bỏ các từ chức năng (giới từ/mạo từ: on, the, of, by...) còn treo lơ lửng ở cuối.

2. khong_khi (aesthetics) là danh sách tag mood tiếng Anh rời rạc (vd "elegant, historical, serene"), không phải câu mô tả — gây 71% prompt long bị loại (24/34). Sau khi hỏi ý kiến, quyết định: chỉ giữ MỘT tag nổi bật nhất làm gợi ý văn phong cho bước 2a viết, và không đưa vào checklist chấm điểm ở bước 2b nữa — giống cách xử lý "loai_anh"/"goc_chup" mặc định.

Phần còn lại (210 lượt "group_fact", 37 prompt) là nội dung cốt lõi của element — màu sắc, chất liệu, vị trí — nhiều khả năng là chất lượng viết thật của model (đúng việc bước 2b cần bắt), không phải lỗi pipeline; chưa thấy mẫu hình hệ thống nào đáng sửa thêm ở đây.
Toàn bộ fix ở trên đều sửa checklist (1b) — chưa sửa lời dặn cho model (2a)
Mọi fix từ đầu tới giờ đều nằm ở bước 1b (thay đổi checklist — cái gì được coi là "đúng"), chưa đụng tới STEP2A_SYSTEM (lời dặn thật sự đưa cho model viết prompt). Soi lại thấy một lỗ hổng thật ở đó: anh_sang/boi_canh vẫn bị thiếu thường xuyên ngay cả ở mức long (dư từ, không phải do hết ngân sách) — vì system prompt chỉ cấm THÊM tin ngoài bản mô tả, chưa từng nói rõ phải nhắc đủ mọi mệnh đề được cho. Model có thể tự ý bỏ bớt ánh sáng/bối cảnh mà không phạm luật nào.

Sửa: thêm một dòng bắt buộc — "phải nhắc đến đầy đủ mọi mệnh đề được cho, kể cả scene; được diễn đạt lại tự nhiên hơn nhưng không được bỏ sót". Bốn ví dụ few-shot đã sẵn làm đúng việc này (đều nhắc đủ phần scene của chính nó) nên không cần sửa, chỉ cần nói rõ thành luật tường minh để model khái quát đúng cho những trường hợp ngoài few-shot.

Hệ quả: đơn vị chấm điểm là mệnh đề
Vì chiều sâu bị cắt nên desc không còn nguyên văn. Thay vì hỏi "element e0 có xuất hiện không", ta hỏi từng mệnh đề một: "có thuyền không? · có màu tím không?"

Ở mức short, checklist chỉ có "thuyền gỗ" — nên model tự thêm "quán ăn nổi, có người đội nón lá đang nấu" không bị trừ điểm, ngược lại còn được tính vào chỉ số Độ dày.
Ba lỗi lắp checklist đã sửa (phát hiện từ dữ liệu server thật)
Thiếu thông tin cảnh (scene). loại ảnh / góc chụp / ánh sáng / không khí / bối cảnh được đưa vào bước 2a để viết prompt nhưng ban đầu không được đưa vào checklist — bước 2b lọc dựa trên checklist thiếu này nên cứ thấy prompt nhắc tới ánh sáng, góc chụp... là báo "thêm tin" oan. Tỉ lệ đạt rơi từ ~60% xuống 4–8%. Sửa bằng cách luôn thêm giá trị scene vào checklist.

Trùng chủ thể giữa các thành viên trong nhóm bị xoá nhầm. Khi hai thành viên một nhóm có cùng danh từ chủ thể (hai "người phụ nữ", hai "bông tai vàng"), bước lắp checklist từng khử trùng theo văn bản trên toàn nhóm — làm mất luôn danh từ chủ thể của thành viên thứ hai, để lại một thuộc tính mồ côi không chủ thể. Model viết đúng (dùng cardinality để suy ra "một cô khác") nhưng bị chấm sai vì checklist thiếu. Sửa: bỏ khử trùng liên-thành-viên, mỗi thành viên giữ đủ mệnh đề của riêng nó.

Tên nhóm văn hoá bị rơi khỏi checklist khi nhóm đã có sẵn mệnh đề khác. Tên riêng của nhóm văn hoá (vd "thanh đồng trong lễ Hầu đồng") trước đây chỉ được thêm vào checklist khi nhóm đó không có mệnh đề nào khác — nếu nhóm đã có 8 mệnh đề từ các element con thì tên nhóm không bao giờ vào checklist, dù model viết đúng tên vẫn bị báo "thêm tin". Sửa: nhóm văn hoá luôn có tên trong checklist, bất kể đã có mệnh đề khác hay chưa.
Xung đột thật: luật "PHẢI ĐẦY ĐỦ" (bước 2a) vs ngân sách từ short/medium
Sau khi bước 2a được yêu cầu phải nhắc đủ mọi mệnh đề (xem callout tương ứng ở bước 2a), đo lại checklist short trên test_6: tổng số từ cộng dồn của các mệnh đề p50=19, p90=30, max=44 từ — trong khi length_hint short chỉ 8-20 từ. Ở đuôi phân phối, checklist đòi hỏi nhiều hơn hẳn những gì một câu 20 từ có thể chứa được, bất kể diễn đạt cô đọng cỡ nào — mâu thuẫn trực tiếp với luật "phải nhắc đủ". Nguyên nhân: các trần trước đó (group_element_cap, max_cultural_groups, element_cap) đều giới hạn theo số element/nhóm, chưa có trần trực tiếp theo tổng số từ.

Sửa: thêm max_checklist_words theo mức (short: 16, medium: 50, long: không giới hạn) — sau khi lắp xong checklist đầy đủ, cắt bớt theo đúng thứ tự ưu tiên GIỮ (mệnh đề nhóm theo salience → dòng "số lượng" → scene), không bao giờ cắt một nhóm xuống dưới 1 mệnh đề (vì 2a vẫn thấy tên nhóm đó qua trường "name", nên checklist phải còn ít nhất một mệnh đề tương ứng để không chấm oan). Kết quả đo lại: short p90/max còn đúng 16 từ; medium còn đúng 50 từ.
Chủ thể chính bắt buộc — tín hiệu độc lập rút từ TÊN FILE
required_group_index = việc "nhóm nào là chủ thể chính" hiện chỉ dựa vào salience do step1a (LLM) tự xếp — nếu step1a lỡ xếp sai, không có gì đảm bảo checklist còn giữ đúng chủ thể chính (vd "hủ tiếu Nam Vang", "rước kiệu"). Tên file trong bộ dữ liệu này lại chính là slug không dấu của chủ thể chính thật (ruoc_kieu_002128.json → "rước kiệu", hu_tieu_nam_vang_001001.json → "hủ tiếu Nam Vang") — một tín hiệu độc lập với salience của step1a.

Dùng tín hiệu này để: (1) ép nhóm khớp filename luôn được giữ ở mọi mức, kể cả khi nó không phải nhóm chính và không phải nhóm văn hoá theo step1a; (2) đưa mệnh đề rank-0 của nhóm đó vào required_subject — ở bước 2b, thiếu đúng mệnh đề này thì loại ngay lập tức, không phụ thuộc --max_missing. Không có ràng buộc riêng này thì việc nới lỏng --max_missing để giảm tỉ lệ loại có thể vô tình cho lọt đúng trường hợp nguy hiểm nhất: prompt thiếu hẳn chủ thể chính nhưng vẫn đạt vì mọi mệnh đề thiếu được xét ngang hàng nhau.

Không đổi thứ tự nhóm (group 0 vẫn do step1a quyết định) — chỉ thêm một ràng buộc riêng, độc lập, để tránh rủi ro reorder nhầm khi slug khớp nhầm nhóm.
2a Sinh user prompt LLM
Đầu vào
  • sub_json + persona
Đầu ra
  • user_prompt (văn xuôi tự nhiên)
Rủi ro lớn nhất của bước này
Nếu chỉ bảo LLM "viết prompt từ bản mô tả này", nó sẽ cho ra một bản dịch xuôi của JSON — liệt kê từng vật thể, dùng ngôn ngữ khung hình ("nằm ở góc trên bên trái"), bám đúng thứ tự JSON. Đó không phải giọng người dùng. System prompt phải chặn đúng các hành vi đó.

System prompt

Bạn đang đóng vai NGƯỜI DÙNG muốn nhờ AI tạo một tấm ảnh.
Bạn được cho một bản mô tả có cấu trúc. Hãy viết ra CÂU YÊU CẦU của bạn.

BẮT BUỘC
- Viết như người ĐANG ĐẶT HÀNG một bức ảnh chưa tồn tại,
  KHÔNG phải người đang mô tả một bức ảnh có sẵn.
- Chỉ nói những gì có trong bản mô tả. Cấm thêm thông tin mới.
- Giữ NGUYÊN VĂN thuật ngữ tiếng Việt (áo dài, bánh tét, chợ nổi Cái Răng...).
- Độ dài: {8-20 | 30-60 | 100-200} từ.

CẤM
- Cấm liệt kê từng vật thể thành từng mệnh đề riêng.
  Gộp vật cùng loại: "ba chiếc thuyền gỗ", "mấy người đội nón lá".
- Cấm ngôn ngữ kỹ thuật về khung hình: "nằm ở góc trên bên trái",
  "chiếm phần dưới khung hình", "ở tiền cảnh".
  User thật nói "phía sau", "bên cạnh", "ở giữa".
- Cấm bám theo thứ tự bản mô tả. Bắt đầu bằng thứ bạn quan tâm nhất.
- Cấm văn dịch. Viết như người Việt nói chuyện.
- Cấm lặp một khuôn mở đầu; đa dạng cách vào câu.

PERSONA: {vai} · {giọng} · {ngôn ngữ}

Kèm 3–5 ví dụ few-shot viết tay. Với nhiệm vụ bắt chước văn phong, few-shot hiệu quả hơn hẳn mô tả bằng luật.

TrụcGiá trị
Vai60% user phổ thông · 40% còn lại chia đều: designer · khách ngành cưới–sự kiện · sinh viên · marketing
Ngôn ngữ80% tiếng Việt · 20% tiếng Anh nhưng giữ nguyên thuật ngữ Việt (áo dài, khăn xếp…)

Persona chỉ đổi cách viết, không đổi nội dung — nên cùng một sub_json với 5 persona khác nhau sẽ cho 5 prompt khác nhau nhưng chung một thước đo chấm điểm.

Ví dụ — trên ảnh chợ nổi Cái Răng có thật (7 element)
short   "Ảnh chụp từ trên cao chợ nổi Cái Răng với mấy chiếc thuyền gỗ"     (13 từ)

medium  "Chụp từ flycam chợ nổi Cái Răng trên sông nước đục, ba chiếc thuyền
         gỗ neo gần nhau, một chiếc màu tím bán đồ ăn, mấy người đội nón lá
         đang nấu nướng."                                                   (36 từ)

long    "Mình muốn ảnh chụp từ trên cao cảnh chợ nổi Cái Răng. Mặt sông rộng
         màu nâu đục chiếm gần hết khung hình. Ở giữa là chiếc thuyền gỗ dài
         màu tím làm quán ăn nổi, có người đội nón lá đang nấu. Bên trên là
         thuyền chở đầy sọt trái cây, phía dưới là chiếc thuyền xanh chở
         khách ngồi thành hàng."                                            (68 từ)

Ba hành vi người thật, đọc ra được từ chính ví dụ trên:

Hành viTrong ví dụ
Gộp, không liệt kê "ba chiếc thuyền gỗ" — JSON tả riêng từng chiếc thành 3 element
Bỏ hẳn đồ vặt Cái xô nhựa đỏ (element 17 từ) không xuất hiện ở bất kỳ mức nào, kể cả long
Đảo thứ tự tự nhiên Chủ thể → bối cảnh → không khí. JSON thì background trước, element thứ tự ngẫu nhiên
Ngoài phạm vi: lỗi chính tả
Mọi prompt sinh ra ở bước này đều viết đúng chính tả, đủ dấu. Việc chịu được đầu vào sai chính tả, mất dấu hay viết tắt ("chup anh nhom ban truoc lang bac") thuộc về một mô-đun correction riêng, đặt trước prompt enhancer trong chuỗi xử lý.

Lý do tách ra: nhiệm vụ chính của mô-đun này là chi tiết hoá. Trộn thêm nhiễu chính tả vào dữ liệu huấn luyện sẽ bắt model học hai việc cùng lúc, làm nhoè cả hai và khiến phần đánh giá khó quy trách nhiệm khi có lỗi.

Kiểm soát chất lượng: chạy thử 50 mẫu và tự đọc trước khi đốt 56k lượt gọi. Nếu thấy nhiều câu kiểu "một chiếc thuyền gỗ dài màu tím được đặt nằm ngang ở trung tâm khung hình" thì system prompt còn hở — sửa rồi mới chạy tiếp.

2b Lọc chất lượng LLM khác họ
Đầu vào
  • cặp (sub_json, user_prompt)
Đầu ra
  • Cặp đạt · Cặp bị loại

Kiểm tra prompt không thêm và không thiếu so với sub_json. Dự kiến loại 15–20%. Bỏ bước này thì sub_json hết là thước đo đáng tin, và toàn bộ phần đánh giá sập theo.

Chỉ chấm hai điều: THIẾU và THÊM. Ban đầu có thêm tiêu chí "văn máy móc/ dịch máy" nhưng đã bỏ hẳn — không phải việc của bước lọc này, để dành cho một mô-đun correction riêng nếu cần sau này.

Ngôn ngữ không quan trọng, trừ một ngoại lệ
Giám khảo (bước 2b) không được báo thiếu/thêm chỉ vì prompt diễn đạt bằng ngôn ngữ khác với mệnh đề gốc — mệnh đề ghi "bright overcast daylight", prompt viết "ánh sáng ban ngày dịu, trời âm u" thì vẫn tính là đã nhắc tới.

Ngoại lệ duy nhất: thuật ngữ văn hoá Việt Nam (áo dài, khăn xếp, chợ nổi Cái Răng, thanh đồng, lễ Hầu đồng...) — những tên này bắt buộc giữ nguyên tiếng Việt. Dịch "áo dài" thành "Vietnamese dress" hay "thanh đồng" thành "shaman" vẫn bị tính là thiếu.
Mệnh đề vị trí: không cần lặp tên chủ thể, nhưng giá trị vị trí phải đúng
Một số mệnh đề vị trí lặp tên chủ thể/nhóm ở cuối câu (vd "ở tai phải thanh đồng"). Prompt viết tự nhiên thường không lặp lại tên đó cho từng chi tiết — chỉ thiếu tên chủ thể lặp lại thì không tính là thiếu. Nhưng phần vị trí cụ thể (trái/phải, tay/tai/cổ...) vẫn phải khớp đúng: "...bông tai vàng bên tai phải" → đạt; "...bên tai trái" → sai vị trí, vẫn tính thiếu; không nhắc bên nào cả → thiếu.
2b2 Sửa lại prompt bị loại LLM · tuỳ chọn — --retry_rejected
Đầu vào
  • Cặp bị loại + lý do (missing/extra từ 2b)
Đầu ra
  • Cặp đạt (đã sửa) · Cặp thật sự bị loại

Mặc định prompt bị 2b loại là mất trắng, dù phần lớn lỗi (thiếu 1-2 mệnh đề, thừa 1 chi tiết) hoàn toàn sửa được thay vì phải sinh lại từ đầu. Bật --retry_rejected (mặc định tắt) thì sau bước 2b, step2b2_correct.py đưa đúng lý do bị loại (thiếu gì, thừa gì) cho một lượt gọi LLM sửa lại — CHỈ sửa đúng phần bị nêu lỗi, không viết lại từ đầu — rồi chấm lại bằng đúng judge của 2b (kể cả ràng buộc required_subject ở bước trước). Đạt thì gộp vào tập đạt (đánh dấu corrected: true, giữ original_prompt để audit); vẫn fail thì mới thật sự loại.

Retry ĐÚNG 1 lần, không lặp thêm
Chỉ sửa một lần duy nhất rồi chấm lại — đủ cho lỗi nhỏ (thiếu/thừa 1-2 mệnh đề), chi phí thêm đúng 1 lượt gọi model cho mỗi prompt bị loại, không có rủi ro lặp vô hạn. step2c_split.py tự phát hiện và gộp corrected_passed.jsonl nếu bước này đã chạy, không cần cấu hình gì thêm ở 2c.
Cờ liên quan: tắt hẳn cổng lọc (--ignore_judge)
Thêm cờ ở bước 2b: khi bật, KHÔNG gọi judge, mọi prompt được coi là đạt — không chấm gì cả. Dùng khi debug hoặc muốn tin thẳng đầu ra của 2a. Cả hai cờ (--retry_rejected, --ignore_judge) đều tắt theo mặc định, không đổi hành vi cũ nếu không bật.

4 Huấn luyện SFT LoRA
Đầu vào
  • X = user_prompt
  • Y = target_json
Đầu ra
  • LoRA adapter

Một model duy nhất (LoRA trên Qwen3.6-27B) cho cả 3 mức. Không tách 3 model: dữ liệu có hạn, và phần khó nhất — schema cùng kiến thức văn hoá Việt — là chung cho cả ba. Code: code/train/.

Điểm mấu chốt của toàn bộ thiết kế
Cả 3 mức prompt dùng chung một nhãn Y là target_json đầy đủ. Prompt short nghèo thông tin nhưng nhãn vẫn giàu → model buộc phải học cách lấp đầy khoảng trống. Đó chính là năng lực "chi tiết hoá" mà ta cần.

Nếu train prompt short với nhãn là sub_json, model sẽ học đúng thói quen tai hại: nhận prompt ngắn thì trả JSON ngắn — và ảnh sinh ra sẽ hỏng.
Mỗi mức một system prompt riêng — không phải một tag chung
Ban đầu định dùng MỘT system prompt chung, chỉ thêm một dòng DETAIL_LEVEL: short|medium|long để phân biệt. Nhưng việc model cần làm ở mỗi mức thực sự khác hẳn nhau — gộp vào một dòng tag là không đủ, nên đã đổi hướng: mỗi mức có system prompt riêng biệt (chung một phần schema/luật văn hoá, khác phần hướng dẫn hành vi):
  • short — chỉ 8-20 từ, nêu vài ý chính. Model phải tự bổ sung chi tiết hợp lý để JSON vẫn đầy đủ như một caption chuyên nghiệp.
  • medium — 30-60 từ, đã nêu vài ý rõ. Giữ nguyên phần đã có, lấp phần còn thiếu.
  • long — 100-200 từ, gần đầy đủ. Việc chính là cấu trúc hoá trung thành, hạn chế tối đa tự thêm.
Hệ quả bắt buộc: ứng dụng gọi model lúc inference phải biết trước đang phục vụ mức nào để chọn đúng system prompt — giống hệt lúc train. Không có cách nào để model tự suy ra mức mà không lệch train/infer. Ba file system prompt (một cho mỗi mức) được lưu kèm adapter sau khi train xong.
